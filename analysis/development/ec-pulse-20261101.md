# Original EC network pulse: capture reinspection

The existing recordings show a strong, heartbeat-relative **200 ms transmit
grid**, a **10-second heartbeat**, promptly dispatched acknowledgements, and
some repeat bursts that intentionally appear to skip every third grid slot.
This is stronger evidence for a slot-based scheduler than for a fixed delay
between arbitrary sends. It does not yet prove a switch receive duty cycle or
exclusive timeslots allocated to individual peers.

Reproduce with `python3 tools/analyze_ec_pulse.py`. Full measurements, input
hashes, packet references, excluded-window caveats and the local comparison are
in `analysis/development/ec-pulse-20261101.json`. This was offline analysis;
no firmware, configuration, daemon or hardware was changed.

## Clock and transmit slots

Ten original-EC captures were examined: the five supplied recordings, live
pairing, the known one-gang control session, the five-minute app session, and
the two power-loss/recovery sessions. Relays were excluded from gateway
transmission statistics by requiring native source `9bf4ea38` and family `8c`.
Periods without a recent captured heartbeat were excluded from phase analysis.

The broadcast, zero-subject `8c/08` heartbeat normally arrives every approximately
10.0007 seconds; its counter advances by ten. Dividing each capture's median
regular heartbeat period by 50 gives an observed grid of approximately
200.014 ms. The small difference from 200 ms is consistent with relative clock
rate error; it is not evidence that software should literally request 200.014 ms.
Power-off gaps and missed heartbeats are retained separately.

Across captures with an eligible preceding heartbeat:

| Measurement | Result |
|---|---:|
| Original EC output packets within 1 ms of a grid edge | 108/116 |
| First observed output attempts within 1 ms | 61/64 |
| Median absolute grid error, all output packets | 0.204 ms |
| First-attempt 95th percentile absolute grid error | 0.259 ms |
| First-attempt ages after heartbeat | 0.200–9.601 seconds |
| First-attempt slots occupied, out of 50 per heartbeat | 38 distinct slots |
| Output trailers encoding exact multiples of 200 ms | 108/116 |

Thus EC does not wait for the next ten-second heartbeat before every output
command. It appears able to start a command at many 200 ms edges throughout the
cycle. The phase trailer independently corroborates the measured RF grid.
A minority of transmissions are displaced by approximately 2–14 ms; contention,
processing delays or another scheduling rule remain possible explanations.

Maintenance `0a`, `11`, query `10`/`ac`, and registration responses also cluster
around this grid, with larger offsets in some maintenance sequences. They
should not be merged with reactive ACK traffic into one timing distribution.

For all 64 first observed output attempts, there was **no decoded packet in the
preceding 50 ms** at this receiver. We found no consistent immediately preceding
radio message acting as a per-command trigger. The heartbeat is a timing anchor;
app/cloud request arrival is not visible in these RF recordings. Absence at one
receiver does not prove there was no uncaptured packet.

## Switch response phase and reactive ACKs

In `original-ec-live-20261025`, 59 native `9e/05` state reports from six peers
fell 8.627–18.664 ms after their nearest grid edge (median 14.115 ms). This is a
**position within a slot**, not an assertion that every state report arrives
14 ms after the command: it can arrive in a later slot or be unsolicited.

Across the inspected captures, 294 gateway acknowledgements were matched to a
preceding native report using source/destination, subject, opcode and MAC
sequence. Their delay was 2.004–2.142 ms, median 2.081 ms. These replies follow
the incoming report promptly; they do not wait for the next 200 ms edge.
Registration acceptance replies were treated separately from these reactive
ACKs.

## A repeating 600 ms pattern in longer retries

The earlier description of 400 ms gaps as potentially missed packets needs
refinement. There are sequences with **consecutive MAC sequence numbers** that
regularly alternate 400 and 200 ms:

- `original-ec-75710834-control-01`, frames 423–467: 13 copies of one output
  command, MAC sequences 97 through 109. Relative slots are
  `0, 2, 3, 5, 6, 8, 9, 11, 12, 14, 15, 17, 18`. The twelve gaps alternate
  400 and 200 ms, all within roughly 0.12 ms of those nominal intervals.
- `original-ec-live-20261025`, frames 1492/1493/1499/1503: four copies, consecutive
  sequences 117–120, relative slots `0, 1, 3, 4`.
- The same live recording, frames 1684/1690/1694/1697/1699: five copies,
  consecutive sequences 130–134, relative slots `0, 2, 3, 5, 6`.

These support a recurring **two transmissions per three 200 ms slots** pattern
in some longer bursts. Consecutive sequence numbers make missing gateway
retransmissions a weaker explanation here. The phase of the skipped slot varies;
we have not established a universal 600 ms superframe, a fixed slot per device,
or the reason for skipping. Short bursts frequently contain a single 200 ms
repeat. A fixed 400 ms retry interval does not reproduce either pattern.

## Difference from our current output path

In the recent 200/400 ms experiment, 159 local output packets had an eligible
captured local heartbeat. Only 4/159 were within 2 ms of its 200 ms grid, and
none of the 45 eligible first attempts were within 2 ms. Median absolute grid
error was 59.855 ms for all packets and 66.296 ms for first attempts, compared
with approximately 0.2 ms for original EC.

The local tests measured approximately 213.7 or 413.6 ms between adjacent
retries. Both start at an arbitrary phase; UART/radio overhead then adds roughly
14 ms of phase drift per retry. Doubling the host wait therefore changes retry
frequency without reproducing EC's clocked transmission pattern.

The most direct next experiment is to dispatch the **first output command and
its retries at absolute MCU heartbeat-relative 200 ms boundaries**, retaining
the same six-attempt limit, four-second deadline, fresh-report stop condition,
and immediate ACK timing. First test alignment alone; test the observed
200/400 alternation separately if needed. The previous AC-only query alignment
tests did not align output-control transactions and do not resolve this case.

## Is more EC traffic needed?

No additional capture is needed to establish the pulse or justify an aligned
output experiment. More controlled traffic would help explain slot skipping:
record one EC-controlled switch, isolated app ON/OFF actions separated by five
seconds, and enough repeats to capture several longer retry bursts, with no
physical presses or other app actions. Ideally record the same sequence once
with other EC switches powered and once without them, when convenient. That
would help distinguish a gateway retry schedule from mesh/peer interactions.
The current captures cannot prove the receive-window mechanism, app-arrival
latency, or why a specific slot is skipped.

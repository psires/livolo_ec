# Nordic PCA10059 0.12 bring-up, 2026-11-01

The user identified the official PCA10059. It is on the main Pi, 10.1.1.21.
Sonoff has moved to 10.1.1.120 and passed an independent comparison as the
[replacement passive sniffer](sonoff-sniffer-20261101.md). The TI CC2652P remained
the active Docker-managed gateway during passive Nordic bring-up. After those
checks, TI was disarmed and the existing Docker daemon/registry handed to Nordic.
No retry or query-timing setting was changed.

The Nordic port is implemented in [firmware/nrf52840](../../firmware/nrf52840/README.md).
It reuses the existing packet/peer/phase/scheduler core, with native USB CDC,
0 dBm raw channel-11 radio, and unchanged query/output timing and retry limits.
The image reserves factory MBR, bootloader and settings; only application HEX
ranges are packaged. Both gateway and official stock-sniffer recovery packages
are saved on the Pi and locally. The stock recovery is not a readback of the
originally installed application.

## Bring-up checks

- 183 shared gateway unit tests pass after the portable platform selection change.
- A new compiled-C clock regression test protects synchronous LF startup readiness.
- Application-only flash through the preserved Nordic Open DFU Bootloader works.
- Candidate 03 enumerated as `cafe:4001`, with stable FICR serial
  `f1bf2323f452d37e`, and reported firmware **0.12**, protocol 3 and
  `board=nordic-pca10059`.
- Passive radio reception included the test one-gang switch `66780945` and live
  original EC traffic. No Nordic RF transmission was enabled for these checks.
- All 12 dry protocol checks passed, including all 256 peer slots, ACK policy,
  session/lease guards, duplicate handling, overflow rejection and no RF TX.
- Scheduler clock, pending work, cancellation and lease-expiry checks passed
  without RF transmissions.
- All **6,000** alternating long CHECK/CAPS requests passed in approximately
  **51 seconds**, with no reply mismatches, timeouts or new USB/software queue
  loss counters. Nordic raw receive-error counters did increase; these include
  air CRC/filter failures and are not equivalent to USB overruns. Later source
  separates CRC, filter and runtime errors for meaningful RF qualification.
- The first normal application `BOOTLOADER` trial entered factory DFU
  without a button but lost its final reply during USB teardown. A 20 ms final
  drain fixed that; the final application returned the reply and completed a
  full software-triggered DFU/reflash/restart cycle successfully.

## Startup fault and recovery test

The first two candidates stalled during radio startup. Source inspection found
that `nrf_802154_lp_timer_init()` synchronously waits for its LF-clock callback.
The adapter had deferred that callback to the main loop, which could not run
until initialization returned. Candidate 03 delivers LF readiness immediately,
while deferring HF notifications to avoid radio-driver reentrancy. That candidate
passed the checks above.

A separate deliberate-stall image tested an interrupt-independent
TIMER4/PPI0/GPIOTE0 self-reset path. It **did not return to DFU**. The user found
that pressing RESET while plugged in did not recover this image, but holding
RESET while reconnecting USB did. GPIO ownership by the experimental mechanism
is a possible explanation, not a proven root cause. That mechanism and its
self-test build option have been removed entirely. The bounded follow-up
self-test was never flashed. No autonomous stall-recovery claim is made.

The normal application has now been restored. Its `BOOTLOADER` command returned
`OK BOOTLOADER`, entered factory DFU without a button, accepted the same final
application again, and restarted with configured/armed/peer counts all zero.
The final candidate passed the dry, scheduler and 6,000-request USB checks again.
TI was then explicitly disarmed before handing the unchanged Docker daemon and
host registry to Nordic. Active control and the 603.611-second continuous observation passed, with the
Sonoff sniffer recording independently on 10.1.1.120. Nordic is left active.

## Final candidate and active qualification

The final application occupies `[0x1000, 0xcf68)` and is 49,000 bytes as a
binary. Its SHA-256 is
`3816bfbfbcfa87f02f97b075efb3fd64764c50ee0d15f7a7ee0d1cf132f8bf28`.
The stack starts at `0x20040000` and the Thumb reset vector is `0x9b79`.
No MBR, bootloader, settings or UICR ranges were flashed. Adding `_Noreturn`
to the self-reset helper removed a compiler diagnostic without changing the
application binary hash. Exact file/package hashes are in `image-final.json`.

Final passive verification repeated all 12 dry checks, the scheduler check and
6,000 exact USB requests in 50.976 seconds, with zero mismatches, timeouts or
new transport/queue-loss counters. Application update and reset verification
is in `final-dfu-check.json`; `update=none` remains correct because Nordic open
DFU is separate from the TI signed-update protocol.

The initial active block confirmed **24/24** output commands: eight each for
the one-gang output and both two-gang outputs. Twenty-two transactions used two
attempts and two used three, under the unchanged maximum of six attempts and
four-second deadline. Sonoff captured **50/50** successful output transmissions
and **23/24** exact reports retained by the Nordic MCU. Missing a report in the
independent sniffer does not invalidate the matching report received by Nordic.
Both test outputs were restored to their pre-test states: `66780945` ON and
`46715621` output 1 OFF / output 2 ON. Pairing remains disabled.

The completed 720-second Sonoff recording contains 7,144 packet records, with
zero ESN1 CRC errors, sequence gaps, resynchronization bytes, or increments in
its radio/UART/timestamp loss counters.

Timing is measured relative to captured heartbeats, correcting the constant
oscillator-rate difference using their ten-second spacing. A capture supplies
relative radio timing; its absolute wall-clock offset comes from the first
host-received record and is not a synchronized RF time reference.
The previous TI settled block confirmed 24/24 with 48/49 transmissions captured;
ZB-GW04 confirmed 24/24 with 48/48 captured. These sequential, differently placed
radio trials do not isolate hardware effects from changing RF conditions.

The intentional dry malformed-line test left `input_errors=1`. RX/UART output
counters also increased while USB had no consumer between passive checks and
handover. Active-test qualification compares increments, not boot-lifetime zero.
Raw radio CRC/filter errors are tracked separately from USB loss and driver
runtime errors. Host `invalid_rx` also counts unsupported EC frames, so it is
not a USB corruption counter.


## Continuous observation and deployment

The observation lasted **603.611 seconds**, with one radio session, no Docker
restart, both peers online and MQTT connected. RX/UART/metadata drops, input
errors, radio queue drops, driver runtime errors, radio TX timeouts, host RX gaps
and ACK failures all had **zero increments**. TI and ZB-GW04 were explicitly
disarmed; their TX/ACK counts did not increase during the check.

| Independent Sonoff measurement | Result |
| --- | --- |
| Output sends / retained reports captured | 50/50 sends; 23/24 reports |
| Retry spacing | Median 199.995 ms; 199.572–200.838 ms |
| Absolute output-grid error | Median 0.034 ms; maximum 0.883 ms |
| Captured local heartbeats in live window | 60, with no missing ten-second interval |
| Heartbeat spacing | Median 9999.793 ms; 9999.772–9999.816 ms on the sniffer clock |
| Automatic ACKs | 24 captured, all phase-stamped; 23 matched incoming frames |
| Matched ACK response delay | Median 1.693 ms; 1.688–1.712 ms |
| ACK encoded-phase error vs captured heartbeat age | Median +0.244 ms; +0.151–+0.342 ms |

Nordic counted 511 CRC failures and 15 filter/length failures during the live
window, with no driver runtime failures. These are receive-air diagnostics,
not application USB failures. The host's `invalid_rx` counter increased by
3,426 and includes unsupported frames; that aggregate alone cannot identify
transport corruption. Replaying the independently captured live-window frames
through the host decoder yielded 5,573 unsupported-frame rejections and 523
accepted packets, with no other decoder error. The two radios can hear different
packets; those counts cannot explain every host rejection one-to-one.
No original gateway heartbeat from `9bf4ea38` was captured
in this window. Other transmitters remained audible, so this does not establish
a quiet RF environment or a controlled EC-on/off comparison.

Docker remains the sole live-radio owner. The only environment change was
`LIVOLO_SERIAL_DEVICE`: `/dev/ttyAMA0` became the stable Nordic application by-id
path. The image, configuration JSON, Compose YAML, daemon environment and
registered device identities were preserved. The native service remains disabled
and stopped. Restricted database/configuration backups stay on the development
Pi under `nrf-port/private-backup`; they are not copied into public evidence.

This qualifies this board and these two devices for the tested bounded workload;
it does not establish long-term/many-peer reliability. Query reliability remains
tier 3 and was not used as a reason to alter retry limits or timing. Software DFU
is verified, but an unresponsive application may still need manual recovery.

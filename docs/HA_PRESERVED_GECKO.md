# Internal preserved-Gecko installation boundary

This is a source-only worker adapter and a proposed service contract, prepared
2026-11-08. It does not register an HTTP API, CLI or app mode and cannot be
selected through the installed HA integration. Physical eligibility remains
disabled. The separate [provisioning model](HA_RADIO_PROVISIONING.md) remains
simulated; its journals and evidence must never be admitted as physical jobs.

## Internal worker

`host/livolod/preserved_gecko.py` exposes `install_preserved_gecko` only to a
future trusted parent. It accepts immutable GBL bytes and their admitted digest,
the exact `zb-gw04-1v2` profile, a parent-held lease descriptor, a durable
acknowledgement callback, and injected endpoint/loader/application providers.
Those physical providers are not implemented in this chunk. Tests supply all
I/O; no serial port, scan, reset, helper process or physical flash is performed.

The parent must independently establish and journal:

- Operator-confirmed exact board/revision, selected USB topology/interface,
  attachment generation and current device number. CH340 `1a86:7523` and a
  generic by-id name identify a transport, not the PCB or its flash layout.
- Unique target and enforceable exclusive ownership across the daemon and
  other apps. The current target has no USB serial, so no serial is invented.
- The supported preserved Gecko loader/version and upload/security mode on
  that endpoint. Historical ZB-GW04 loader 1.9.2 is not a fresh probe result or
  a universal allowlist. No Sonoff reset wiring is reused; PD4 is not a boot pin.
- A trusted exact-board application artifact, source/digest/notices and a
  reviewed recovery route. Inspection alone is not qualification.

The callback result `owner: exclusive` is a **parent assertion of evidence**,
not evidence generated by this module. A validated regular-file guard is a
cooperative lease, not global exclusion of ZHA, Zigbee2MQTT or unrelated apps.
Namespace-limited process inspection is insufficient by itself. The future
deployment must prevent competing access and target replacement during the
interval between the last identity check and the helper opening its pathname.
Otherwise installation remains blocked. The adapter does not stop other apps.

The worker validates GBL tags/ranges/compiled identity with the existing
application inspector before physical callbacks. Only application writes in
`0x4000..0x30000` are accepted; loader, SE and token writes are excluded. It
checks the pinned `universal-silabs-flasher` 0.0.31 helper, validates the inherited
guard, checks endpoint evidence, probes the selected loader at 115200, and
rechecks endpoint identity. Probe providers receive a three-second timeout and
must honor it without reset, fallback scanning or automatic retry.

The parent must durably record the `flash` boundary before acknowledging it.
After that acknowledgement the worker rechecks the guard and endpoint, then
invokes the existing fixed helper on a private immutable staged file. No reset,
force, erase, helper-path or board overrides are accepted from an API client.
There is no normal-update newer-version check here: same-version installation
belongs only to this separate explicit provisioning operation. Existing routine
update admission remains unchanged.

After transfer, independent `VERSION`, `CAPS` and `STATUS` projections must
agree on exact board/version/protocol 3/application baud 460800, with `armed=0`
and `ack=0`. Endpoint identity is checked before and after these reads.
No `NETWORK`, `ARM`, pairing or switch command is sent. The returned receipt
says `application_verified`, `network_ready: false`, `setup_required: true` and
`image_readback_verified: false`. Its artifact digest identifies the transferred
bytes; it is not a full-flash readback or proof of preserved factory settings.

The **parent must commit the receipt** before presenting success or permitting
handoff. A process exit, helper return, or callback return alone is insufficient.
Failure after possible transfer raises `GeckoInstallError` with a stable code,
phase, `mutation_possible: true` and `recovery_required`. Before-transfer failures
retain `mutation_possible: false`. If the parent already journaled an uncertain
boundary, its more conservative recovery state takes precedence. Restart must
never replay an installation automatically.

The parent must supervise the worker and its descendants with a bounded total
lifetime and retain the lease until all children exit. The adapter itself is a
synchronous worker function, not a process supervisor or a durable controller.
Its injected providers must obey their timeout contracts. Transfer progress is
stage-only because the reused helper does not expose measured byte progress;
the adapter invents no percentage.

The shared helper waits at most 120 seconds for transfer, then three seconds
after terminate and three seconds after kill. Bounding the final reap fixes its
previous unbounded wait. A final timeout does **not** prove child exit or lease
release: the outer supervisor must retain/reconcile descendant ownership and
report recovery, never success. The earlier private candidate built from
`6ae80d7` does not contain this later cleanup fix or the internal adapter.

## Proposed HA bootstrap and handoff contract

This section is design-only. A future physical service uses a separate
authenticated `/api/v1/provisioning` namespace and a persistent service-instance
identity. Bootstrap identity never replaces a Livolo network identity. Every
response identifies schema, service instance, operation and physical/simulated
mode. Hardware eligibility is an explicit server capability; helper presence or
a USB bridge name is insufficient.

| Proposed action | Side-effect boundary |
| --- | --- |
| Info/target/status/job GET | Stored/static facts only; no serial access or retries |
| Prepare POST | Explicit **Inspect radio / Prepare installation** action; may inspect the exact loader under ownership |
| Install POST | Explicit confirmation of an expiring immutable plan with durable request ID |
| Operation-result GET | Reconcile prepare/install/handoff by their existing request IDs |
| Handoff POST | Separately acknowledged transition to normal daemon operation |

Preparing an install differs from the existing read-only firmware check: actual
loader verification uses serial I/O. It therefore needs its own explicit action,
durable idempotency record and result lookup after response loss. The resulting
expiring plan binds target attachment, exact board evidence, loader identity,
artifact digest and ownership. Installation revalidates those facts, without
accepting arbitrary paths, URLs, serial selections or helper/reset commands.

Explicit bootstrap startup mode must keep the normal `Service` radio reconnect
and restore loop stopped. The proposed smallest app arrangement runs the
bootstrap listener on the native API port instead of the normal radio service,
preserving existing options, credentials, network configuration and database.
An unconfigured new installation must not manufacture a gateway/tag simply to
pass the normal config parser. Mode selection and app registration need a
separate implementation/review gate; none is included here.

Application verification is not hub readiness. A separately idempotent handoff
resumes the normal daemon using preserved configuration. The same provisioning
journal, instance identity and operation results remain readable afterward.
Existing HA URL, credential, entry ID, network ID, devices and entities remain
unchanged. HA accepts completion only after normal info and snapshot agree with
the expected network and report readiness. A changed network or service
identity stops the flow; it does not create or replace an entry automatically.
Lost handoff replies are reconciled from durable results and normal API identity,
never by replaying installation. The existing coordinator's network-identity
checks must not be relaxed to accommodate bootstrap status.

For a new network, choosing and persisting its configuration is a separate
acknowledged step. Create the HA entry only after normal API verification.
The initial preserved-loader experiment can validate an existing network without
claiming stock-reset entry or complete first-time setup. Real API paths beyond
the namespace, wrapper registration and the maintenance observer remain to be
implemented and jointly reviewed.

## Validation scope

With the [contributor test environment](../CONTRIBUTING.md) activated:

```sh
PYTHONPATH=host:host/tests python -m unittest test_preserved_gecko -v
```

Tests use synthetic GBL bytes, temporary local lease/journal files, and injected
I/O. They cover durable parent acknowledgement, post-ack target replacement,
loader/security/owner rejection, artifact/flash-range failures, helper failure
and cleanup, independent postflight mismatches and firmware-only receipts.
They do not prove global physical ownership, actual loader behavior, calibrated
flash preservation, RF functionality, hardware recovery or HA deployment.

Release Engineering owns private candidate build/image evidence and rollback;
ZigBee owns live target/loader/recovery qualification; HA owns the maintenance
observer and guided UI; Unix owns the worker and future bootstrap service.
No source-only result creates public artifact or catalog eligibility.
